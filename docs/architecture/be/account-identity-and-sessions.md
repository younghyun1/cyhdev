# Account identity and session invariants

Email addresses and user names are unique without regard to letter case. Emails are stored lowercase; user names keep the case a person typed for display. PostgreSQL enforces both through the `users_user_email_lower_unique` and `users_user_name_lower_unique` expression indexes on `lower(...)`, and every identity lookup compares `lower(column) = lower($1)` so it uses them. Registration classifies conflicts by index name without a race-prone existence query.

A signup whose email already exists is settled in one transaction. If that account is unverified, it takes the new submission's password hash, user name, and geography, its earlier verification tokens are deleted, and a fresh link is sent; its sessions are revoked. Whoever registered the address first therefore loses it to the next submitter, and only the newest link verifies. A verified account is never changed. A user name held by another account returns the same 409 whether or not the email exists, and every other path returns the same accepted response, so responses do not reveal registered emails.

The identity migrations take an exclusive lock and fail closed when existing rows collide, exactly at first and case-insensitively since September 23. They never delete, rename, or merge an account. An operator must choose the canonical account, repair references and identity values explicitly, and rerun the migration. Each down migration restores the previous uniqueness rules.

All account, email-verification, password, and role mutations are coordinated by `AccountService`. Repositories commit database changes; the service then updates the process-local session store. Password changes, verification, and account removal revoke every session of the account. Role and profile changes refresh sessions from committed data; if that authoritative read fails, the service revokes every affected session before returning the committed mutation result. A bounded read/write coordination gate lets logins proceed concurrently while excluding session-affecting mutations through commit and refresh or revocation. This prevents an in-flight old-password login from recreating a session after a password reset, and prevents concurrent role changes from publishing stale session state.

Each such commit and its session follow-up run on a spawned task that the request awaits. A client disconnect drops only the wait, so it cannot leave a committed reset, deletion, verification, or role change without its revocation, refresh, or live-chat anonymization.

Unverified accounts never receive sessions. Login with the correct password for an unverified account returns 403 with error code 68 and no cookie; a wrong password returns the usual 401. Verification revokes instead of upgrading sessions because a session opened before verification could belong to whoever registered the address first.

Database-current Younghyun authority checks for long side effects, such as Minecraft RPCs and i18n synchronization, hold a separate authority lock rather than the session gate. Role, permission, deletion, and hard-purge mutations take the authority lock before the session gate, so a queued role change waits behind a slow administrative operation without stalling logins.

Sessions are intentionally process-local because this backend is deployed as one process. PostgreSQL has no sessions table and authenticated requests do not query the database. Restarting the process invalidates every session by design; running multiple backend processes would create independent, incoherent login state and is unsupported.

## Session credential and lookup

Each successful login obtains 32 bytes from the operating-system CSPRNG. The role is read in the same query as the credentials, so a successful login makes no second database round trip before creating its session. The browser receives those bytes as a 43-character unpadded base64url value in the `__Host-cyhdev-session` cookie. The cookie is host-only because it has no `Domain` attribute; it also has `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and a one-hour `Max-Age`. JavaScript cannot read it, but the browser sends it on credentialed same-origin requests.

The session store never retains the bearer token. It computes `SHA-256(secret)` and uses the full 32-byte digest as the key in a concurrent `scc::HashMap`. Middleware rejects any token that is not exactly 43 bytes of canonical base64url, decodes into a fixed stack buffer, hashes it, and performs one expected O(1) map lookup. The outer login-status middleware publishes its lookup result as a request extension, and the inner authentication gate reuses it, so each request performs that lookup once. Invalid input cannot cause an input-sized allocation. A successful lookup clones only bounded session authority; the user name uses `Arc<str>` so the common clone does not copy its allocation.

Sessions expire after one hour. Lookup removes an expired entry immediately. The maintenance purge and capacity admission path also remove expired entries. The store reserves admission with an atomic counter before insertion, so concurrent logins cannot exceed the fixed 16,384-session limit. One account holds at most 16 sessions; a new login first removes that account's oldest sessions, so one set of credentials cannot fill the store. When the store is still full, admission purges expired entries once and then returns an explicit HTTP 503 error rather than growing memory or evicting another account's session.

Login rotates only the valid session token already presented by that browser. Other browsers and devices retain independent sessions. Password, verification, and identity changes revoke every session for the user; profile authority and role changes refresh every unexpired session from committed account data. Logout removes only the presented session and sits outside the authentication gate, so any session, whatever its state, can end itself. The raw token and its derived key are never logged.

## Security boundary

The cookie replaces a shared frontend API key, not browser trust. A copied cookie remains a bearer credential until its one-hour expiry, explicit logout, user-wide revocation, or process restart. `HttpOnly` prevents direct cookie reads through page JavaScript, but an active same-origin script injection can still issue requests as the user. Exact trusted-origin checks on unsafe requests and WebSocket handshakes remain required alongside output encoding and the application content-security policy.
