# Account lifecycle and retained tombstones

Account deletion preserves authored content while removing the account as an authentication and public-profile identity. The `users` row is permanent because posts, comments, photographs, live-chat history, votes, and other records retain its `user_id` foreign key. The lifecycle migration replaces authored-content cascade and `SET NULL` foreign keys with named `ON DELETE RESTRICT` constraints so an accidental user-row deletion cannot erase content or violate registered-chat sender checks.

## Soft deletion

`DELETE /api/auth/account` is a protected route under the existing exact-Origin gate. It requires the current password even when a valid session exists. `AccountService` takes the session-consistency write lock, verifies the password against the active account, and asks the repository to perform one row-locked transaction.

The transaction copies the current name, email, ISO country, ISO language, and optional subdivision into `deleted_account_retention`. It does not retain a password hash. It then deletes linked OIDC provider identity, role assignments, and password-reset and email-verification tokens; marks the email unverified; replaces the name, email, and password with unique non-credential tombstone values; copies the protected system actor's valid country and language; clears subdivision; and sets `user_deleted_at` with `user_purge_after` 30 days later. Persisted live-chat sender names become `Deleted user` while internal `user_id` attribution remains. Authored photograph latitude and longitude are zeroed transactionally; first hard purge repeats chat-name and coordinate scrubbing to cover writes that began before soft deletion committed.

The database enforces paired deletion timestamps, purge ordering, hard-purge ordering, and system-actor protection through named checks. A named delete trigger rejects physical deletion of every lifecycle tombstone and system actor, including accounts whose only remaining references are cascading vote rows. A separate update trigger makes system-actor status and deleted tombstone identity irreversible while permitting the initial soft-delete transition and the later one-way hard-purge timestamp. Active non-system rows remain deletable for explicit pre-lifecycle administrative repair, subject to their foreign keys. The nil UUID user is marked as a system actor by the migration. Every future system actor receives the same protection when `user_is_system_actor` is true.

Only after the transaction commits does the service revoke every process-local RAM session and anonymize bounded live-chat cache entries. Already-open registered-user sockets receive a targeted shutdown and are rejected by message and RTC paths until their last connection unregisters. A pending WebSocket registers before rechecking the same RAM session, so deletion either invalidates that recheck or observes and closes the registered connection without a database lookup. Restart remains a full session invalidation boundary; account lifecycle does not add a database session lookup.

Login, session refresh, current-account lookup, public-profile lookup, password reset issuance, and account-existence checks filter out deleted rows. The unique live identity values are freed by replacing them in `users`; the originals remain private during the grace period.

`PATCH /api/auth/profile` updates the complete editable profile surface: user name, ISO country, ISO language, and optional subdivision. Email is intentionally absent and remains read-only. The current password is confirmed with the same non-session-invalidating error contract as self-deletion. The repository locks the active user, verifies the unchanged password hash, validates country and language existence plus subdivision ownership, and classifies the named user-name uniqueness constraint. After commit, the service refreshes all RAM sessions from PostgreSQL and revokes them if refresh fails.

Profile pictures are retained as bounded history. `user_profile_picture_is_active` identifies the selected image; a partial unique index permits at most one active row per user, while zero active rows means the default avatar. Migration activates only the newest usable cloud-backed row and fails closed on inconsistent legacy cloud/link pairs. Current and public profile reads select only the active row. History listing, selection, deletion, and overflow cleanup use the shared durable media ledger.

## Retained-content presentation

Public adapters detect deletion through batched author reads of `users.user_deleted_at`, including startup cache hydration. Blog posts and comments, photographs and photograph comments expose the nil UUID and exact display name `Deleted user` instead of the retained actor identity. Live-chat messages expose a null user ID and the same display name. Profile links, country values, and photograph coordinates are masked. Content IDs, text, ordering, pagination, and aggregate vote totals remain unchanged, so deletion does not corrupt conversation structure or ranking.

## Hard purge

`POST /api/admin/users/{user_id}/hard-purge` is behind authentication and the superuser middleware. The API passes the authenticated requester ID through the service; in the purge transaction the repository locks that requester's active user row, verifies the current PostgreSQL role is exactly `Younghyun`, and only then locks the target. This prevents a stale RAM role from authorizing purge after demotion. It rejects active targets, protected system actors, and requests before `user_purge_after`. In one transaction it deletes the private retention row and sets `user_hard_purged_at`. It never deletes the `users` tombstone or authored content. Repeating the request after hard purge is safe and resumes any profile cleanup still represented by profile-picture metadata.

Remote object deletion cannot be atomic with PostgreSQL. Profile-picture rows therefore act as a retry ledger: non-cloud metadata is finalized directly; cloud metadata remains until its S3 deletion succeeds. A crash between remote deletion and metadata finalization is safe because object deletion is idempotent. Each request processes at most 256 ledger rows in indexed creation order, and the final metadata transaction recounts remaining rows before the response reports deleted counts, exact remaining work, and current-batch failures. It never reports full cleanup while failed or unprocessed object metadata remains.

Superseded profile objects use the durable `media_object_cleanup` ledger. Resolvable rows have a unique bucket/key pair; legacy rows may retain a both-null address with their original URL until reconciliation. Attempts, timestamps, and bounded errors support ordered retries. `GET /api/admin/media-cleanup/unresolved` lists at most 100 unresolved rows, and `POST /api/admin/media-cleanup/{cleanup_id}/resolve` sets a bucket/key only when the caller supplies the exact stored original URL. Both routes repeat the database-authoritative superuser check. A named profile-picture check requires future cloud status and links to be paired; migration fails closed if legacy rows violate it.

## Pre-purge notification

Soft deletion creates two notification-ledger rows in the same transaction as private identity retention: seven days and 24 hours before the immutable 30-day purge deadline. PostgreSQL generates UUIDv7 row IDs and enforces one row per retained user and stage. Existing retained accounts are backfilled by the notification migration. The ledger references the permanent `users` tombstone with `ON DELETE RESTRICT`; update and delete guards make notification identity, attempts, and terminal audit state one-way. Hard purge removes the retained email without erasing sent, failed, or cancelled delivery evidence.

The minute worker claims at most 32 due rows ordered by `(next_attempt_at, notification_id)` using `FOR UPDATE SKIP LOCKED`. One UUIDv7 batch token and a ten-minute expiry make claims restart-safe and prevent overlapping workers from delivering the same active claim. Before delivery, one bounded query inner-joins the claim with `deleted_account_retention`; missing private retention makes the row non-deliverable. Within the single-process deployment, a read/write gate prevents hard purge from removing retained email during the revalidation-to-SMTP interval. Hard purge cancels every unsent row and clears its claim before deleting private retention.

Delivery runs with concurrency four and also acquires the shared 16-slot SMTP admission permit. Each stage uses its durable notification ID as a stable RFC 5322 `Message-ID`, so a crash after SMTP acceptance but before the sent-state commit retries the same message identity. Failed attempts clear the claim, retain only an identity-free error class bounded to 512 characters, and schedule a five-minute exponential delay capped at 1,280 minutes. Successful attempts set `sent_at` and clear claim and error state. Logs contain aggregate counts and stage/error classes only; retained names, email addresses, user IDs, notification IDs, and transport errors are not logged.

`GET /api/admin/account-retention-notifications` returns at most 100 identity-minimized rows with a `(next_attempt_at, notification_id)` cursor. `POST /api/admin/account-retention-notifications/{notification_id}/retry` clears an unsent due row's claim and queues it immediately. Both routes repeat the database-authoritative superuser check. They cannot retry a sent, cancelled, not-yet-due, or retention-less row.

There is no automatic purge. The legacy hourly job that hard-deleted expired unverified users remains disabled because it bypassed retention and cannot satisfy authored-content foreign keys. Hard purge remains explicit and separately authorized. The lifecycle and notification migration down paths succeed only before lifecycle state exists; after scheduling or deletion they fail closed and require backup-based recovery.
