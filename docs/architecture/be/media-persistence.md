# Media persistence

Image endpoints accept PNG, JPEG, GIF, WebP, TIFF, and BMP, and `image` is built with only those decoders plus the AVIF encoder. The declared MIME type selects one decoder; a file whose signature disagrees is rejected before decoding, so no other codec is reachable from an upload.

The two photograph endpoints, both limited to administrators, also accept `image/avif`, and store that file byte-for-byte instead of encoding it. Re-encoding drops a file's embedded metadata; storing the original keeps its EXIF (capture time, GPS position, camera and lens), XMP, colour profile, bit depth, and HDR signalling, and avoids a second lossy generation. The stored object is public, so whatever the file embeds, including a precise GPS position, is published with it; the map position shown on the site is still the one entered in the upload form. The server checks only that the file opens with an `ftyp` box naming the `avif` still-image brand: no AV1 decoder is built in, so an AVIF original is never decoded, and its pixel dimensions are not bounded beyond the 150 MiB upload limit. Because the server cannot decode the original, it cannot derive the thumbnail from it. The browser renders each AVIF to a JPEG of at most 1,600 pixels and sends it in the same request: a `thumbnail` part on `/api/photographs/upload`, and a `thumbnail` part directly after the AVIF's `files` part on `/api/photographs/batch-upload`, where position is the pairing. That rendering is limited to 8 MiB, must be one of the decodable types, and goes through the normal bounded decode and AVIF encode to become the 800-pixel thumbnail. An AVIF without a thumbnail part is refused, and so is a thumbnail part sent with any other type, which keeps a thumbnail from differing from a photograph the server can decode itself. Profile pictures and demo thumbnails still refuse AVIF, because they must be resized. `features/photography/service/photograph_source.rs` owns this choice for both endpoints.

Image endpoints stage multipart file fields to automatically removed temporary files through a 64 KiB userspace buffer. The staged encoded input is never accumulated into a request-sized `Vec<u8>`. The capture time is read from the staged path's EXIF, in an AVIF container as in the other formats; processed AVIF output is written to temporary files through another 64 KiB buffer, and S3 reads those files as path-backed byte streams.

Image decoding is globally limited to two concurrent jobs, and the permit moves into the blocking task so a cancelled request cannot free a slot while encoding continues. Every AVIF variant uses rav1e speed 1, the slowest preset, at quality 80; encoder-managed threading has no application-specified thread cap. This prioritizes compression over encode time. Speed does not change pixel dimensions, but it can change file size and decoded appearance; no representative-photo comparison has been measured. Each source is rejected above 16,384 pixels on either axis or 64 Mi pixels in total, and the decoder receives a 256 MiB allocation limit. Photograph variants are produced largest-to-smallest from one decoded image, so thumbnail creation does not decode or clone the original a second time. Batch processing additionally limits end-to-end item concurrency to four, bounding simultaneous object-store and database work. Batch originals keep their EXIF, including GPS, so each batch stages them, and the rendered thumbnail image of each AVIF, in its own 0700 temporary directory with 0600 files; directory names carry a per-process token, and the startup sweep removes only directories left by earlier processes.

Uploaded objects carry `Cache-Control: public, max-age=31536000, immutable` because every key embeds a fresh UUIDv7 and is never overwritten. Object-store and database ordering is centralized in `util::media::persistence`. New objects upload first. If a later upload or the database commit fails, every new object uploaded by that attempt is deleted in reverse order. Compensation failures are returned with the original failure and retain an explicit retry-safe classification.

Profile-picture replacement locks the active account row, deactivates the prior selection, inserts the new active metadata, and retains the eight newest valid pictures. Overflow metadata is removed only after the same transaction inserts a `profile_picture_history_pruned` cleanup row containing the original URL and, when validation succeeds, its exact bucket and key. Invalid legacy URLs remain unresolved for the separately authorized reconciliation API. The partial unique active-row index and user-row lock preserve one active picture under concurrent upload, selection, and deletion. Authenticated history APIs list the bounded set, select an owned entry atomically, and enqueue an owned object before deleting its metadata; deleting the active entry selects the newest remaining valid picture.

The same ledger protects photograph image and thumbnail deletion, WASM thumbnail deletion, and superseded WASM thumbnails. Source metadata is never deleted or overwritten before all corresponding cleanup rows are committed. Resolved rows are deleted immediately after the metadata transaction; successful idempotent deletion removes the ledger row, while failure increments its attempt count and records a bounded error. Unresolved rows are never guessed. The photograph API accepts at most 1,000 distinct IDs, sorts and deduplicates them before database or S3 work, and returns explicit deleted, failed, unresolved, and remaining counts.

The maintenance worker scans at most 256 resolved rows in stable `(last_attempt_at NULLS FIRST, created_at, id)` keyset order, attempts at most 32 deletions per run with concurrency four, and applies exponential backoff from 30 seconds to one hour. This service is intentionally single-instance; idempotent object deletion and compare-by-attempt-count ledger updates still make overlap between a request and the periodic worker safe.

`tests/integration/media_cleanup_compensation.rs` uses the object-store interface with a recording fake. It verifies database-failure cleanup, partial-upload cleanup, post-commit superseded deletion, successful cleanup reporting, and bounded persisted errors. `tests/integration/postgres/profile_picture_history.rs` covers the eight-entry cap, unique active selection, active fallback on deletion, and durable overflow/deletion rows.
