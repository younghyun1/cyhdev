# Media persistence

Image endpoints accept PNG, JPEG, GIF, WebP, TIFF, and BMP, and `image` is built with only those decoders plus the AVIF encoder. The declared MIME type selects one decoder; a file whose signature disagrees is rejected before decoding, so no other codec is reachable from an upload. Image endpoints stage multipart file fields to automatically removed temporary files through a 64 KiB userspace buffer. The staged encoded input is never accumulated into a request-sized `Vec<u8>`. EXIF reads from the staged path, processed AVIF output is written to temporary files through another 64 KiB buffer, and S3 reads those files as path-backed byte streams.

Image decoding is globally limited to two concurrent jobs, and the permit moves into the blocking task so a cancelled request cannot free a slot while encoding continues. Each AVIF encode uses at most half the cores; thumbnails use rav1e speed 8 and full-size images the default speed 4. Each source is rejected above 16,384 pixels on either axis or 64 Mi pixels in total, and the decoder receives a 256 MiB allocation limit. Photograph variants are produced largest-to-smallest from one decoded image, so thumbnail creation does not decode or clone the original a second time. Batch processing additionally limits end-to-end item concurrency to four, bounding simultaneous object-store and database work. Batch originals keep their EXIF, including GPS, so each batch stages them in its own 0700 temporary directory with 0600 files; directory names carry a per-process token, and the startup sweep removes only directories left by earlier processes.

Uploaded objects carry `Cache-Control: public, max-age=31536000, immutable` because every key embeds a fresh UUIDv7 and is never overwritten. Object-store and database ordering is centralized in `util::media::persistence`. New objects upload first. If a later upload or the database commit fails, every new object uploaded by that attempt is deleted in reverse order. Compensation failures are returned with the original failure and retain an explicit retry-safe classification.

Profile-picture replacement locks the active account row, deactivates the prior selection, inserts the new active metadata, and retains the eight newest valid pictures. Overflow metadata is removed only after the same transaction inserts a `profile_picture_history_pruned` cleanup row containing the original URL and, when validation succeeds, its exact bucket and key. Invalid legacy URLs remain unresolved for the separately authorized reconciliation API. The partial unique active-row index and user-row lock preserve one active picture under concurrent upload, selection, and deletion. Authenticated history APIs list the bounded set, select an owned entry atomically, and enqueue an owned object before deleting its metadata; deleting the active entry selects the newest remaining valid picture.

The same ledger protects photograph image and thumbnail deletion, WASM thumbnail deletion, and superseded WASM thumbnails. Source metadata is never deleted or overwritten before all corresponding cleanup rows are committed. Resolved rows are deleted immediately after the metadata transaction; successful idempotent deletion removes the ledger row, while failure increments its attempt count and records a bounded error. Unresolved rows are never guessed. The photograph API accepts at most 1,000 distinct IDs, sorts and deduplicates them before database or S3 work, and returns explicit deleted, failed, unresolved, and remaining counts.

The maintenance worker scans at most 256 resolved rows in stable `(last_attempt_at NULLS FIRST, created_at, id)` keyset order, attempts at most 32 deletions per run with concurrency four, and applies exponential backoff from 30 seconds to one hour. This service is intentionally single-instance; idempotent object deletion and compare-by-attempt-count ledger updates still make overlap between a request and the periodic worker safe.

`tests/media_cleanup_compensation.rs` uses the object-store interface with a recording fake. It verifies database-failure cleanup, partial-upload cleanup, post-commit superseded deletion, successful cleanup reporting, and bounded persisted errors. `tests/postgres_profile_picture_history.rs` covers the eight-entry cap, unique active selection, active fallback on deletion, and durable overflow/deletion rows.
