# Minecraft map tile cache

`/minecraft/map/` serves squaremap's generated public directory from `SQUAREMAP_WEB_DIR`. Its tile middleware uses the async `scc::HashCache` interface. Cache guards never cross filesystem awaits. PNG terrain tiles are cached on demand; JSON, other assets, noncanonical paths, files larger than 8 MiB, and range/date-precondition requests use `ServeDir`. `If-None-Match` takes precedence over `If-Modified-Since` on cached responses. HTML documents receive an in-memory storage shim for the opaque-origin sandbox and are therefore served in full without validators; see [browser security headers](browser-security-headers.md).

The cache has a fixed 4 GiB allocation budget. A 64 MiB reserve covers the index, whose capacity is limited to 65,536 entries. Tile buffers consume byte permits before allocation, charged at their exact length plus 1 KiB per entry and twice the relative path length. The reserve and per-entry allowances cover cache bookkeeping conservatively; this is not a bound on the Rust process RSS or the operating system page cache. Request handling, TLS, and transient filesystem I/O buffers consume additional memory.

Each tile owns its byte reservation. HTTP bodies retain that owner through shared `Bytes`, without copying the tile. Eviction cannot release the reservation while a response still references the data. Concurrent cache fills are limited to 16. Ordinary eviction uses scc's bucket-local LRU. When byte reservations run out, one asynchronous reclamation pass removes at most 256 entries. If space is still unavailable or reclamation is busy, the request falls back to streaming from disk. Cache space never causes requests to wait for other clients to finish.

Every lookup checks device, inode, size, and nanosecond modification/change timestamps. Cache misses read an open file and compare its metadata before and after reading; changed files bypass insertion. Missing files remove the cached entry. The metadata tuple also supplies a weak ETag. Tile responses require browser revalidation, and live JSON uses `no-store`. A concurrent writer can change the file after validation, as with normal filesystem serving; the next lookup detects the new version.

The cache is empty after a website restart and requires no separate worker or service. Deployment follows the existing website binary workflow. Unit tests exercise small budgets, retained response buffers, concurrent fills, same-size rewrites with preserved modification time, atomic replacement, deletion, path filtering, and bypass limits. HTTP tests cover ETags, HEAD, range fallback, query-string reuse, and uncached JSON updates.
