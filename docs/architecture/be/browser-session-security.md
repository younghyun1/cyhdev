# Browser session security

Browser bundles cannot hold a confidential shared credential. Every `VITE_*` value is compiled into public JavaScript, and a browser user controls the network client. The application therefore does not send a global API key from the frontend. Authentication uses an individual server-issued session cookie; machine credentials, if later required, must authenticate only a separately scoped non-browser route and remain in server-side configuration.

The session cookie is `Secure`, `HttpOnly`, host-only, scoped to `/`, and `SameSite=Strict`. `HttpOnly` prevents application JavaScript from reading it, but it does not protect a session from the person controlling the browser, developer tools, the operating system, or a compromised extension. The security boundary is that one browser receives only its own revocable session, never a credential shared by every deployment user.

Credentialed CORS and side-effect authorization share one `TrustedOrigins` policy. Production defaults are `https://cyhdev.com` and `https://www.cyhdev.com`. `TRUSTED_BROWSER_ORIGINS` adds comma-separated exact origins for split-origin deployments. Configured URLs are reduced to their canonical origin serialization before comparison. Local mode also permits `https://localhost:30737` and the standard localhost Vite origins; plain HTTP is limited to `localhost` and loopback IP addresses. Dev, staging, and production require HTTPS. Every mode rejects wildcard, `null`, user-information, non-root paths, queries, fragments, malformed values, missing request origins, and duplicate request origins; invalid configuration aborts startup.

Every method other than GET, HEAD, and OPTIONS requires one exact trusted `Origin`. A GET carrying a WebSocket upgrade also requires one, which covers both host-stat and live-chat handshakes. This gate prevents cross-origin side effects; CORS alone only controls whether a browser exposes the response. The admin i18n synchronization endpoint is POST so it is covered by the same rule.

Local development should use HTTPS end to end or a same-origin Vite proxy because secure cookies are never sent over plain HTTP. Session authority is the fixed-capacity process-local store documented in `account-identity-and-sessions.md`; the `__Host-cyhdev-session` cookie contains a 256-bit opaque credential, only its SHA-256-derived key remains in RAM, and restart invalidates all sessions. Tokenized GET flows such as email verification still need a separate confirmation or POST design to avoid link-prefetch consumption.
