# Minecraft controls

The lazy `/admin/minecraft` route provides a server-controls panel within the Admin workspace, visible only after login and superuser status are confirmed. The public `/minecraft` page contains only the map. It sends typed requests to cyhdev, never directly to Minecraft. The backend supports global literal-text messages, whitelist listing/add/remove/enable/disable, online-player listing and kick, world save, and restart. It exposes no arbitrary command or shell interface. The map and its tile cache are independent of the controls.

`GET /api/admin/minecraft` reads players, whitelist membership, and whitelist status. `POST /api/admin/minecraft/actions` accepts a closed tagged action enum. Both routes inherit session authentication, superuser checks, and private response headers. Mutations additionally require the existing trusted-origin check. Before reaching Minecraft, the account service rechecks current database authority and holds its authority lease through the operation, excluding concurrent account-service role changes. No database connection or transaction is held over network I/O.

The Rust transport uses Minecraft's JSON-RPC management API over authenticated WebSocket connections to `127.0.0.1`. Configuration consists of `MINECRAFT_MANAGEMENT_PORT` and `MINECRAFT_MANAGEMENT_SECRET`. Missing configuration disables controls; partial or invalid configuration prevents startup. The secret remains server-side. TLS is disabled only on this loopback connection; browser traffic still uses the website's HTTPS connection. RCON remains disabled. See the [Paper configuration reference](https://docs.papermc.io/paper/reference/server-properties/) and [Minecraft management protocol introduction](https://www.minecraft.net/ja-jp/article/minecraft-java-edition-1-21-9).

Requests open short-lived TCP_NODELAY connections, without polling or a connection pool. A single nonwaiting operation slot prevents overlapping management work. Mutations impose a process-wide cooldown: two seconds normally, ten seconds for save, and sixty seconds for restart. Reads can inspect state during a cooldown. A status request has a ten-second timeout; a mutation has fifteen seconds. WebSocket messages and frames are limited to 256 KiB, interleaved notifications to 64 per call, and HTTP request bodies to 4 KiB. Message text is limited to 512 Unicode characters without control characters; player names to 1–16 ASCII letters, digits, or underscores. Literal message encoding prevents command or text-component interpretation.

An acknowledgement means Minecraft accepted the operation, not that saving or restarting has finished. Timeouts, disconnections, and malformed replies produce an uncertain result; neither transport nor UI retries a mutation automatically. The panel preserves failed message text. Restart, kick, whitelist removal, and whitelist access changes require browser confirmation. Audit logs contain actor UUID, method, and acknowledgement status, but not message text or credentials.

## Restart and deployment

Restart calls `minecraft:server/stop`. Minecraft saves and shuts down gracefully; the existing OpenRC `supervise-daemon` restarts the JVM after its configured delay. This does not call `rc-service` or require sudo. If the supervisor itself is stopped, the website cannot start Minecraft. The website does not perform the operating-system shutdown or spawn Java.

On `miniserver`, Minecraft management is enabled at `127.0.0.1:25576`, browser management origins are empty, and matching credentials are configured in `/home/cyh/dist/.env`. Both configuration files have mode `0600`. Pre-change backups are `server.properties.before-cyhdev-controls` beside Minecraft's configuration and `.env.before-minecraft-controls` beside the website environment file. Minecraft was gracefully restarted for activation; the supervisor replaced JVM PID 656121 with 786073. The live read-only check verified required methods and player/whitelist response shapes. No test broadcast, kick, or whitelist mutation was sent to live players.

Website deployment remains required through the existing build/deploy workflow. Frontend assets remain embedded in the Rust binary. No production website binary was built or replaced during implementation. To disable the controls, remove both website environment variables and restart the website. To close the management listener, also disable `management-server-enabled` and restart Minecraft.

## Verification

Backend tests cover input bounds, fixed RPC methods, literal message encoding, malformed/error replies, interleaved notifications, and unauthenticated, non-superuser, or untrusted-origin rejection with uncached responses. The ignored `inspect_live_management` test checks deployment read-only when the management environment variables are supplied; an SSH loopback tunnel can provide access from a development machine. Frontend tests cover private-panel gating, restart confirmation, and no automatic retry after a failed broadcast. Browser checks cover desktop and mobile map layout, Admin navigation, and the control panel with mocked management responses.

## Player map privacy

Squaremap supports `/map hide` and `/map show` for the caller, and operator-only `/map hide <player>` or `/map show <player>` for others. These commands update player visibility live and persist it in Paper player data across reconnects and restarts. The configured tracker interval is three seconds; browsers observe changes on their following refresh. Hiding removes the player from the published tracker data, rather than merely hiding a browser layer. Previously observed positions cannot be retracted. See [squaremap commands](https://github.com/jpenilla/squaremap/wiki/Commands-and-Permissions) and [Paper persistence implementation](https://github.com/jpenilla/squaremap/blob/ac71dd2/paper/src/main/java/xyz/jpenilla/squaremap/paper/PaperPlayerManager.java).

On miniserver, `~/mcserver/permissions.yml` now declares a default-true `cyhdev.map-privacy` parent with only `squaremap.command.hide` and `squaremap.command.show` children. The previous empty file is backed up as `permissions.yml.before-map-privacy`. This permission grant is staged for the next normal Minecraft restart; the active server was not restarted while players were online. It grants no permission to change another player, render maps, or administer the server. The website management API does not expose plugin commands or player visibility mutations.
